# 测试用例：多智能体可验证跨链查询主流程

## 1. 测试用例基本信息

| 项目 | 内容 |
|---|---|
| 用例编号 | TC-MA3C-QUERY-001 |
| 用例名称 | NORMAL 风险跨链查询经过 query-proof、双收集者、commit-reveal 与置信度加权共识后完成提交 |
| 测试对象 | Relayer Demo 查询编排、多智能体协商、query-proof 验证、前端协商摘要展示 |
| 覆盖论文要求 | 验证任务模型、双收集者证据比对、密码学预验证、5 人验证组、commit-reveal、`rep_i * confidence_i` 加权共识、信誉/结算记录 |
| 测试数据 | `orchardBatchId = BATCH-APPLE-0001` |
| 风险等级 | NORMAL |
| 预期阈值 | `n = 5`，`theta = 0.70`，`minimumRevealCount = 4` |

## 2. 前置条件

1. 项目依赖已安装。
2. Relayer 测试环境可运行 Node.js/Jest。
3. 若执行手工 API 流程，需要先启动 demo API 与前端服务。

## 3. 自动化执行过程

### 3.1 执行命令

```bash
cd /mnt/fast18/xunuo/qkl/cross-chain/fabric-chaincode/Relayer
npx jest __tests__/demo/query/query_broker_proof.test.js \
  -t "session gets query proof fields and PASS status" \
  --runInBand
```

### 3.2 执行步骤

1. 测试初始化内存型 `QuerySessionService`、`DemoEventStore`、`AgentRuntime` 和 `NegotiationProtocol`。
2. 创建查询会话：

```js
queryId = "query_1"
orchardBatchId = "BATCH-APPLE-0001"
```

3. 调用 `QueryBroker.run(queryId)` 执行完整查询流程。
4. Relayer 模拟从 FISCO 发起查询请求，并等待 `FISCO_TO_FABRIC` relay 成功事件。
5. Fabric 侧返回果园批次记录，系统构造 `queryObject`、`queryCommitment` 与 `queryProof`。
6. `VerifyQuery` 执行密码学预验证，预期 `queryVerifyStatus = PASS`。
7. 两个 Evidence Agent 生成收集者证明并比对 `evidenceHash`。
8. Agent Runtime 选择 NORMAL 风险验证组，预期选中 5 个验证 Agent。
9. 每个验证 Agent 产生独立判断，写入 `commitHash`、`reasonHash`、`nonce` 与 reveal 结果。
10. 第一轮因缺少补充 header/提交计划进入 `OBSERVE`，第二轮补齐证据后进入 `COMMIT`。
11. 系统生成 `negotiationProof` 与 `settlementResult`。
12. Relayer 模拟 `FABRIC_TO_FISCO` 响应提交成功，最终会话状态变为 `COMPLETED`。

### 3.3 预期断言

测试通过时应满足：

```text
session.status = COMPLETED
session.queryVerifyStatus = PASS
session.negotiationStatus = READY
session.negotiationRound = 2
session.finalProposal.finalDecision = COMMIT
session.finalProposal.risk = NORMAL
session.finalProposal.consensusRule.groupSize = 5
session.finalProposal.consensusRule.threshold = 0.7
session.finalProposal.consensusRule.minimumRevealCount = 4
session.finalProposal.quorum.acceptRatio = 1
session.finalProposal.quorum.wbftSatisfied = true
session.selectedCommittee.length = 5
session.finalProposal.weightVector.length = 5
session.finalProposal.weightVector[*].commitRevealValid = true
```

## 4. 手工 API 执行过程

### 4.1 启动服务

```bash
cd /mnt/fast18/xunuo/qkl/cross-chain
bash scripts/start-demo.sh
```

默认 API 地址：

```bash
BASE_URL=http://127.0.0.1:18080
```

### 4.2 发起跨链查询

```bash
curl -fsS -X POST "$BASE_URL/demo/app/query/request" \
  -H "Content-Type: application/json" \
  -d '{"orchardBatchId":"BATCH-APPLE-0001"}'
```

记录返回的 `queryId`。

### 4.3 查询会话详情

```bash
QUERY_ID=<上一步返回的 queryId>
curl -fsS "$BASE_URL/demo/app/query/sessions/$QUERY_ID?includeProof=1"
```

### 4.4 验证 query-proof

```bash
curl -fsS "$BASE_URL/demo/app/query/sessions/$QUERY_ID/verify"
```

### 4.5 页面观察

打开：

```text
http://localhost:15173/app-query
```

选择对应会话后，应能看到：

1. `VerifyQuery` 卡片显示 `PASS`。
2. `Negotiation` 卡片显示“协商完成”。
3. 风险等级为 `NORMAL`。
4. 置信度加权共识中 `acceptRatio >= 0.70`。
5. Reveal 数满足 `4/5` 或更高。
6. 委员会规模为 5。
7. Commit-Reveal 校验数等于权重向量数量。
8. 仲裁、证明与结算区域显示 negotiation proof digest 与 settlement 分配。

## 5. 通过标准

该测试用例判定通过需同时满足：

1. 自动化 Jest 用例执行结果为 `PASS`。
2. 查询会话最终状态为 `COMPLETED`。
3. `queryVerifyStatus = PASS`。
4. `finalDecision = COMMIT`。
5. NORMAL 风险共识参数为 `n=5, theta=0.70`。
6. 至少 4 个有效 reveal，且所有 reveal 的 commit 校验通过。
7. 前端 `/app-query` 能展示 query-proof 与 negotiation summary。

## 6. 异常判定

若出现以下任一情况，则测试失败：

1. `queryVerifyStatus = FAILED` 或 commitment 校验失败。
2. `selectedCommittee.length < 5`。
3. `commitRevealValid` 存在 `false`。
4. `acceptRatio < 0.70` 且仍然提交响应。
5. `finalDecision` 不是 `COMMIT` 但系统继续触发 `FABRIC_TO_FISCO` 响应提交。
6. API 会话中缺少 `negotiationProof` 或 `settlementResult`。
