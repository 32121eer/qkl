# 跨链可信查询 · 多 Agent 协商模块讲解

> 面向甲方的项目进度说明 ｜ 配合演示页面:`http://localhost:15173/app-query`
> 版本日期:2026-06-10 ｜ 协议:**MA3C(`ma3c-paper-v1`)**

---

## 一、一句话定位

我们在 **Hyperledger Fabric ↔ FISCO-BCOS 双向跨链**之上,做了一层**"多 Agent 协商共识"**:
一条跨链查询的结果,不再由单个中继程序说了算,而是由**一组分布在不同机构、不同服务器上的验证 Agent**,经过**信誉加权投票 + 两阶段承诺揭示 + 行为风控 + 仲裁兜底**,共同裁决"这条结果能不能上链回传"。
最终产出一份**可校验的协商证明**和**信誉结算**。

这套机制直接回答甲方最关心的三个问题:**结果可信吗?谁来背书?出了问题怎么追责?**

---

## 二、演示页面怎么看(app-query 页)

页面一条查询分三段,从上到下对应一次完整的跨链问答:

| 段 | 页面区块 | 含义 |
|---|---|---|
| ① 发起与取数 | 查询卡片 / Query-Proof | 从 FISCO 发起请求 → 到 Fabric(数据链/A 链)取出橙园记录 → 生成查询证明 Π_Q |
| ② **多 Agent 协商** | **Negotiation 面板**(本文重点) | 一组 Agent 对取到的结果做共识裁决 |
| ③ 回传与回执 | 回执卡片 | 协商通过后,把结果连同区块头证据回传 FISCO,落账并出回执 |

本文聚焦**第②段 Negotiation 面板**——它是本项目的技术核心,也是和普通"跨链桥"拉开差距的地方。

## 三、协商面板逐块讲解(屏幕所见 ↔ 背后机制)

Negotiation 面板从上到下共 7 块。下面每块都说明:**甲方在屏幕上看到什么 → 它代表什么机制 → 安全/业务意义**。

### 1. 状态徽章(顶部)
- **看到:** `Negotiation · round N` + 状态徽章(待协商 / 待补证据 / 协商完成 / 协商拒绝 / 协商失败)。
- **机制:** 协商是**多轮**的。第 1 轮验证者若觉得证据未齐(如还差区块头/提交计划),会投"质疑"→ 状态显示**"待补证据"**,系统**自动补充证据进入第 2 轮**;证据齐备后达成**"协商完成"**。
- **意义:** "待补证据"不是错误,而是**审慎**——验证者宁可多要一轮证据,也不轻易放行。

### 2. 最终提案 / 置信度加权共识 / Agent 摘要(三栏)
- **最终提案:** 提案号、**决策(允许提交 = COMMIT)**、风险等级(NORMAL / CRITICAL)。
- **置信度加权共识:** `加权同意率 / 阈值 θ`、`有效揭示数 Reveal x/y`、拒绝率。
- **Agent 摘要:** Approve / Question / 分歧数。
- **机制(WBFT 加权拜占庭):** 每个验证者的票**不是等权**,而是按 `权重 = 信誉 × 置信度` 加权。只有当**加权同意率 ≥ 阈值 θ(NORMAL=0.70)** 且**有效揭示数达标**,才算通过。这比"简单多数"更抗操纵。
- **意义:** 一个信誉差、或自己都没把握(低置信度)的 Agent,**说话分量自动变小**。

### 3. 委员会与权重
- **看到:** 委员会规模、入选 Agent 列表、各自**有效权重**、`Commit-Reveal: x/y`(有效承诺揭示数)。
- **机制:**
  - **风险自适应委员会:** 系统从全部候选 Agent 中,按信誉、时延、**机构多样性**择优选出委员会(NORMAL 5 人,CRITICAL 7 人),其余落入"排除"。
  - **两阶段 Commit-Reveal:** 验证者先提交**密封的投票承诺**,再统一揭示,**杜绝"看别人怎么投再跟票"**。`5/5` 表示 5 票全部通过密封校验。
- **意义:** **防合谋、防跟风、保证多机构背书**——委员会里来自不同机构的 Agent 才算数。

### 4. 风险与威胁模型
- **看到:** 隐性合谋、日蚀风险、**排除节点(含风险值)**、各 Agent 的 risk / success 画像。
- **机制(行为风控):** 后台持续分析每个 Agent 的历史行为——
  - **隐性合谋检测:** 投票高度雷同的 Agent 会被标记;
  - **日蚀/扣留检测:** 长期高时延、反复无效或扣留响应的 Agent 会被标记并降权/排除。
- **意义:** 这是**主动的拜占庭容错**——不是等坏节点投票了才处理,而是**提前把高风险节点挡在委员会之外**。

### 5. 仲裁、证明与结算
- **看到:** 仲裁结论、Proof Digest、结算池 / Slash、各 Agent 的奖惩分配。
- **机制:**
  - **仲裁兜底:** 多轮仍僵持时,启动独立仲裁委员会(5 人 / θ0.75)给出终局裁决。
  - **协商证明(Proof Digest):** 把"谁参与、怎么投、结论是什么、对应哪条结果"打包成一个**可校验的摘要哈希**,任何人都能复核。
  - **信誉结算:** 诚实参与者从结算池**获得激励**;作恶/扣留者被 **Slash 扣罚**。
- **意义:** **可追责 + 有经济激励**——把"做好验证"变成 Agent 的理性选择。

### 6. 结构化分歧
- **看到:** 分歧码列表(如 `HEADER_GAP` 待补区块头、`SUBMISSION_PLAN_PENDING` 待确认提交路由)。
- **意义:** 每一次"质疑"都有**结构化、可读的理由**,而不是黑箱拒绝。协商完成时这里显示"无结构化分歧"。

### 7. 证明校验
- **看到:** Proof Digest / Payload Hash / 协商证明 / 补证请求 的勾选状态。
- **机制:** 对协商证明做**逐项一致性核验**(摘要、提案、决策、承诺、回传载荷哈希、queryId、批次号全部匹配)。
- **意义:** 全绿 = 这次协商的**每个环节都自洽、可独立验证**,可作为对外审计依据。

## 四、一次真实查询全过程(实测数据)

以本次实测的查询 `query_…64eda7cb`(批次 `BATCH-TEST-0099`)为例,完整走通:

1. **取数(A 链):** 从 Fabric 取出橙园记录,`resultFound = true`,查询证明 `queryVerify = PASS`。
2. **协商第 1 轮 → 待补证据:** 委员会中 4 个"均衡"验证者按协议在第 1 轮要求**先确认提交计划/区块头**,投"质疑" → 状态"待补证据"。
3. **自动补证 → 第 2 轮 → 协商完成:** 系统补充证据进入第 2 轮,**5 票全部同意**:
   - **加权同意率 = 1.00 ≥ θ 0.70**,有效揭示 **5/4**,Commit-Reveal **5/5** 全有效,WBFT 满足。
   - 决策 **COMMIT(允许提交)**,风险 NORMAL。
   - 无隐性合谋、无日蚀风险、无分歧。
4. **委员会构成(关键卖点 —— 真正的多机多组织):**

   | Agent | 机构 | 位置 |
   |---|---|---|
   | verifier-balanced-01 | org-c | 本地 |
   | verifier-semantic-01 | org-f | 本地 |
   | verifier-balanced-02 | org-e | 本地 |
   | **verifier-cloud-a2** | org-cloud-a-2 | **云服务器 A** |
   | **verifier-cloud-b2** | org-cloud-b-2 | **云服务器 B** |

   → **5 个委员来自 5 个不同机构、跨 3 台物理位置(本地 + 2 台云服务器)**,共识具备真实的地理与机构分散性。
5. **证明与结算:** 生成协商证明摘要,证明校验**逐项全绿**;结算池按权重发放激励,无 Slash。
6. **回传落账:** 结果连同区块头证据回传 FISCO,**回执 SUCCESS**,三段链上交易全部落账。

## 五、多机多组织部署 与 优雅降级

### 部署拓扑(13 个验证 Agent)
- **本地 5 个**(5 个机构 org-b/c/d/e/f):proof-01、proof-02、balanced-01、balanced-02、semantic-01。
- **云端 8 个**(2 台云服务器,各 4 个 Agent):
  - **服务器 A**(`bjb1`):verifier-cloud-a1 ~ a4
  - **服务器 B**(`bjb2`):verifier-cloud-b1 ~ b4
- 本次已完成两台云服务器的**部署 + 全部 8 个 Agent 上线**,并在真实查询中**云端 Agent 实际入选委员会参与共识**(见上表 a2/b2)。

### 优雅降级(高可用卖点)
- 即使**云端 Agent 全部掉线**,协商仍能**由本地 Agent 独立达成共识并 COMMIT**——系统把不可用节点标为"unavailable"后照常运行,**不影响业务闭环**。
- 这意味着:**多机分散提升可信度,单机/网络故障不阻断服务**,兼顾"去中心化"与"可用性"。

## 八、价值总结(对甲方)

| 关注点 | 本项目的回答 |
|---|---|
| 结果**可信**吗? | 多机构、跨服务器的 Agent 委员会加权共识,非单点背书 |
| 谁来**背书**? | 委员会成员链上可查,协商证明可独立校验 |
| 防**作恶/合谋**? | Commit-Reveal 防跟风 + 行为风控提前排除高风险节点 + 仲裁兜底 |
| 出问题怎么**追责**? | 协商证明 + 信誉结算(奖励诚实、Slash 作恶) |
| **高可用**吗? | 云端掉线可本地降级达成共识,业务不中断 |
| **可审计**吗? | 每条查询产出全绿的逐项证明校验 + 完整链上 tx |
